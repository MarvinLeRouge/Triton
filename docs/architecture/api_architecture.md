# API Architecture

FastAPI application (`api/main.py`), thin transport layer over the engine —
it owns no game logic, only creates/steps a `Simulation` and serializes its
state.

| Endpoint | Purpose |
|---|---|
| `GET /health` | Liveness check |
| `WS /ws/game` | Opens a new `Simulation` per connection, sends its serialized state (`Simulation.to_dict()`) on connect and after every subsequent turn, until the socket disconnects or the game ends |

## Live API reference

The interactive OpenAPI documentation (Swagger UI) is generated by FastAPI
at runtime — run the backend and open `/docs` (e.g.
`http://localhost:8000/docs`, or `http://triton.marvinlerouge.local/api/docs`
behind Traefik). It covers the `GET /health` route; the WebSocket protocol
(message shape sent over `/ws/game`) is not covered by OpenAPI and is
documented instead in the [developer guide](../guides/developer_guide.md).

## Design notes

- One `Simulation` instance per WebSocket connection — no shared state
  across concurrent games, no persistence.
- The turn loop runs server-side on a fixed interval (`STEP_INTERVAL`); the
  frontend is a passive renderer of whatever state it receives.
